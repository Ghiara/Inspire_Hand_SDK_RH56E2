# RH56E2 实机测试与网段迁移

初版以 `task2.md` 为需求参考补充 SDK，旧版 demo 已由用户自行执行。
用户随后运行了带张开/回零阶段的版本，张开阶段出现 30 秒超时。
本轮读取该次本地 JSONL 日志并修正真机到位判断，未重新运行实机命令、控制代码或单元测试。
文档中的实机 CLI 留给用户审阅后运行，未修改设备或电脑网络配置。

## 入口和实现

| 文件 | 用途 |
| --- | --- |
| `example/check_connection.py` | 只读状态采样，默认 MuJoCo，`--real` 才连接 Modbus |
| `example/joint_pos_demo_real.py` | 起始姿态附近的位置往返 |
| `example/joint_velo_demo_real.py` | 带方向的速度参考，软件积分为有界位置命令 |
| `example/target_pos_demo_real.py` | hand_base 中的可达指尖目标，FK → IK → 限速关节命令 |
| `example/real_demos.py` | 参数校验、张开 → 动作 → 原始零位、20 Hz 调度、反馈记录与异常保持 |
| `inspire_sdk/general_control.py` | 四种 controller 的基类，公共状态/停止接口、限速姿态过渡与到位等待 |
| `visualization/feedback_viewer.py` | 将真机采样映射到 MuJoCo 模型，显示主动与联动关节 |

三个 demo 都先执行全手张开并等待反馈到位，然后开始默认仅运动食指的动作阶段。
目标幅度相对张开后的实测姿态默认 ±0.12 rad，参考速度不超过 0.05 rad/s，
保持未选通道的张开参考。速度 demo 保留积分参考，目标被两侧 waypoint 限制，
长时间往返不会积累位置漂移。位置与 3D 模式用相同的参考限速。

动作阶段正常结束后的回零姿态已按用户实机观察修订为 `[0, 0, 0, 0, 0, 1000]`：
前五路回设备原始零位（弯曲端），最后一路拇指根部旋转 `thumb_rotation` 保持张开目标。
这不是模型六轴 0 rad，也不是恢复启动前姿态。张开对应设备六路 `1000`、模型下限；
新零位对应前五轴模型上限、第六轴模型下限。`GeneralController.open_hand()` 和 `return_to_zero()` 均经正常
位置后端限速发送，全部四种模式 controller 都直接继承它们。

闭合轨迹中 `thumb_rotation` 的设备参考从第一条命令起始终为 `1000`，避免根部电机再把拇指
旋向掌心，与正在弯曲的食指相撞。它固定的是张开命令参考，并不强行要求实际反馈必须精确为 1000。
如果 demo 改变过该轴，先单独恢复旋转轴到张开、其他五路保持当前反馈位置，再闭合五路。
恢复与闭合两个子阶段共用回零的超时预算。`pose_status.held_channels` 会标明固定的旋转通道。

两次全手姿态过渡的默认参考速度为 0.2 rad/s，周期沿用 `--period`；每次最多等待 30 秒。
真机只比较 ANGLE_ACT 六路原始反馈与对应的原始目标：误差均不超过 20 个设备单位，
连续 3 个采样周期满足且最终设备参考已经发送，才进入下一阶段。
仿真沿用模型关节 0.01 rad 容差。`--pose-rate`、`--pose-timeout` 调整速度与超时；
`--pose-tolerance-units` 调整真机设备容差，`--pose-tolerance` 只调整仿真 rad 容差。
`--duration` 只计算动作阶段，张开和回零另计；`--channels` 不限制这两个全手动作。
到位超时会中止后续流程并尝试保持，不能把写应答当作已到位。

本轮不添加 Newton 力反馈控制。100 原始单位的 FORCE_SET 是设备阈值，不能按 100 N 解释。
状态读取仍返回六路原始力值，不擅自采用传感器分辨率代替系统标定。
设备原生 FORCE_SET 在位置命令中仍生效，可能先于角度目标停止；不运行软件力反馈并不等于取消设备限力。

新入口缺少 `--real` 时不会构造 Modbus client。真机运动必须先打开窗口，再读取起始反馈，
检查错误码，再设置原始限速/保护阈值和执行全手张开。反馈确认张开到位后预解全部 IK，
再开始动作阶段。窗口初始化、参数检查或初始反馈失败时不写设备。
Cartesian demo 的 FK 目标与 IK 初值均来自同一份张开后实测姿态；优化器只解 --channels 选中的轴，
其余轴固定，且解被限制在起始姿态 ±幅度与机械边界交集内。单独选择一个拇指轴也不会带动另一轴。
只读检查从连接到退出只读 FC03，不调用 `stop()`，不执行自动张开/回零。

真机显示的是反馈姿态，不是另一个独立运动的仿真。每个周期更新主动轴、全部 mimic 关节，
执行 `mj_forward` 更新画面，不执行 `mj_step`。本机估计的指尖位置受 URDF 和角度映射误差影响，
不能用画面当作真实指尖测量。仿真预览使用原有物理后端，保留力矩驱动与 `mj_step`。
真机 `raw_angles` 直接保存原始 ANGLE_ACT，`positions_rad` 明确标记为模型映射估计；
到位不使用画面、仿真 qpos 或 FK 坐标。rad 命令的规划/限速仍使用已有模型映射，尚未标定实物传动。

实机每个控制周期涉及多次同步 Modbus 请求，20 Hz 是目标调度频率，不是保证带宽。
超时停止循环，不重试运动写入；正常结束时等待原始零位到位并保留最终零位目标，再关闭资源。
窗口关闭、Ctrl+C 或异常时尽力发送当前位置保持请求，取消后续自动动作，然后关闭资源。
Ctrl+C 返回 130；故障或通信错误返回 1，保持失败也报告为失败。断网、进程被强制结束或断电时，
软件无法保证发送保持；这里未增加硬件失联看门狗。

JSONL 默认写入 `logs/real_模式_时间戳.jsonl`，仿真为 `sim_`，同名文件不覆盖。
记录起始状态、参数、目标、IK 误差，以及 `opening`、`demo`、`returning_zero` 三阶段的
各周期参考/反馈。最终记录退出原因、`zero_reached` 标志和异常保持结果。
姿态阶段还记录 `pose_status`：比较来源、单位、目标、实际值、误差、容差、阻塞通道及连续到位计数。
终端约每 2 秒显示这些信息，超时异常也保留六轴诊断。
进度还包含当前原始力值、SDK 成功写入的原始力阈值及本段原始力峰值。
到位超时时抛出 `PoseTimeoutError`（继承 TimeoutError），在保持命令改写 ANGLE_SET 之前采集
`read_motion_diagnostics()`，内容包括 ANGLE_SET/FORCE_SET/SPEED_SET/STATUS，只读、不改变参数。
CLI 将其写入 `finish.failure_diagnostics`；支持 `check --diagnostics` 单独查询当前值。
字段读取不支持时保留错误信息，STATUS 保持为固件定义的原始数值。
原来的 `main.py demo` 仍是全手仿真演示，新入口为 `main.py demo-real`，完整 CLI 见 README。

## 网段迁移审查

### 结论与依据

**官方资料确认 RH56E2 提供 IP 配置，能规划到 `192.168.1.xx`；本机设备迁移尚未验证。**
制造商 [RH56E2 User Manual V1.0.0](https://en.inspire-robots.com/wp-content/uploads/2026/09/Dexterous-Hands-User-Manual-for-RH56E2_V1.0.0.pdf)
§1.3.2 给出的默认端点是 `192.168.11.210:6000`，§2.6 的表 41（PDF 第 29 页）
列出 IP 的四个字节地址 `1700–1703`，并注明重新上电后生效。
§2.5 使用 TCP Unit Identifier `0xFF`，SDK 已支持 `--device-id 255`。

这足以确认设备设计支持改 IP；具体固件、Modbus 对单字节字段的打包方式、是否需要额外参数保存，
仍需按随设备资料或厂商工具核对。独立入口 `network_config.py` 默认只读取，先通过配置值与当前
连接地址比对识别编码；无法唯一识别就停止，不发送试探写入。
只有 `--set-ip` 才写 IP 字段并回读校验；额外添加 `--save` 时才向 `1005` 请求全局 Flash 保存。
用户现场记录已确认未保存的修改在断电后恢复旧 IP；新增保存步骤对该固件 IP 的持久化效果待现场确认。
保存请求在 IP 回读通过后才发送，packed 布局将相邻 `1006` 恢复出厂字段编码为 0。
`--host 192.168.1.210` 只改变客户端连接地址，不能替代配置设备。
本次未执行该脚本或离线测试，也未连接实机；命令见 README 的“独立读取和设置灵巧手 IP”。

### 建议地址规划

| 设备 | 当前/已知 | 迁移后的建议（先确认地址未占用） |
| --- | --- | --- |
| 机械臂 | `192.168.1.3` | 保留 `192.168.1.3/24` |
| 灵巧手 | 用户已能 ping `192.168.11.210` | `192.168.1.210/24` |
| 控制电脑有线口 | 用户配置 `192.168.11.212/24` | `192.168.1.212/24` |

以上是地址规划，不是扫描结果。`.3`、`.210`、`.212` 三个地址不同，位于 `192.168.1.0/24`，
避开网络地址 `.0` 与广播地址 `.255`。电脑、手和机械臂仍需连到同一个二层网络/交换机或存在
正确路由；相同网段本身不能跨越隔离网络。同一 `/24` 内的点对点通信不依赖默认网关，
无需把网关设成机械臂 IP。

### 用户后续执行顺序

1. 在当前 `192.168.11.212/24` 配置下先运行 README 的只读检查，保存实际角度、原始力值和错误码。
   ping 成功只说明 ICMP 可达，必须收到完整的 Modbus 响应才能确认 SDK 通信。
2. 记录当前 IP、端口、固件版本和网卡设置；确认目标 `.210`、电脑 `.212` 没有被其他设备占用。
3. 使用匹配设备固件的厂商工具，或独立脚本 `network_config.py --host 192.168.11.210 --set-ip 192.168.1.210 --ip-layout packed-le --save`
   写入目标 IP。脚本先只读核实编码，再按匹配布局写入并回读；未确认编码时停止。
   `--save` 按手册 §2.6.4 请求全局参数保存，不仅是 IP；应答后预留 2 秒再回读配置，不代表已证明断电持久化。
4. 按手册要求重新上电；电脑保留旧网段地址用于回退，并增加新网段地址，再连接新端点：

   ```bash
   # 只读验收；本轮未运行
   PYTHONPATH= python main.py check --real --host 192.168.1.210 --port 6000 --device-id 255 --headless
   ```

5. 再次重启确认新地址持久有效，核对反馈和错误码后再运行运动 demo。
   如果新地址不可达，先核对网卡路由，再从保留的旧地址检查旧端点；不要直接恢复出厂设置。

### 暂不改手 IP 也能集成

同一控制电脑可以保留两个 `/24` 地址：一个访问 `192.168.1.3`，一个访问 `192.168.11.210`。
若两台设备接同一个交换机，可在一个有线口上保留这两个地址；若分属两个独立网口，分别配置。
不需要为了同时控制它们而先改手的 IP，也不需要放宽成 `/16`。

下面只展示一种临时配置方式，**尚未执行**。将 `enp3s0` 换成实际连接的网口，
确认电脑 `.212` 空闲，并避免两张网卡同时拥有冲突的同网段路由：

```bash
# 先查看实际网口和到两个设备的路由（只读）
ip -br -4 addr
ip route get 192.168.11.210
ip route get 192.168.1.3

# 假设此网口已保留 192.168.11.212/24，只额外增加机械臂网段地址
sudo ip address add 192.168.1.212/24 dev enp3s0
# 回退仅删除本次额外地址
sudo ip address del 192.168.1.212/24 dev enp3s0
```

临时配置在断开/重启后可能消失；验证后可在 Ubuntu 有线连接的 IPv4 设置中保存两个地址。
这不改变手或机械臂配置，不代表这两个设备能互相直接通信；当前目标是由电脑分别控制两者。
